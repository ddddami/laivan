# Laivan: Current State and Priorities

Updated: 2026-09-23

## What Laivan Is

Laivan helps people find and assess accommodation in the fragmented FUTA housing
market, then records their intent before they continue with an agent on WhatsApp.
Agents remain part of the market. Laivan's job is to make shared inventory easier
to discover, keep offers attributable, and make coordination more reliable.

The first market is one campus. Expansion to other campuses is a later decision,
after the FUTA workflow produces reliable supply and useful inquiries.

## Marketplace Model

`Property -> PropertyUnitType -> AgentOffer` is the persisted marketplace spine.
A property and its accommodation types are shared canonical records. Different
agents can make offers for the same accommodation type with different prices,
media, descriptions, and availability. Duplication and disagreement are normal
market conditions to manage, not reasons to collapse the model into agent-owned
listings.

Media can belong to a property, an accommodation type, or one agent offer. An
inquiry belongs to exactly one offer. `User` is the application identity; the
same person may seek accommodation and also hold agent or operator access.
Campus bounds inventory and operational permission. Public location remains
approximate, and trust is built from evidence rather than guaranteed by a badge.

## What Exists Today

- The web app provides anonymous discovery, search, filters, property and
  accommodation detail, and competing agent offers. It is a mobile-first PWA.
- Google OpenID Connect provides sign-in. The API owns opaque, revocable sessions
  and enforces CSRF and campus-scoped permissions on protected writes.
- Signed-in users can apply to become agents. Operators can activate, decline,
  suspend, and reinstate agents through protected API routes. Activation creates
  a new linked agent; phone matches do not claim an existing one.
- The API supports canonical contributions and corrections, agent-owned offer
  changes, media upload and soft removal, ETags, and audit records. The admin CLI
  manages privileged role changes.
- A signed-in user can record a question against one eligible offer. The inquiry
  is persisted before an explicit WhatsApp handoff link appears. The web app
  does not open WhatsApp automatically or expose raw agent contact fields.

The web app currently has only public discovery, property and accommodation
detail, and the student inquiry action. It has no agent application, inventory
maintenance, operator review, agent inquiry, or account/logout screen. Those API
capabilities cannot be used through the product UI yet. The repository does not
demonstrate live marketplace liquidity or complete browser/device acceptance.
Automated verification and real PostgreSQL tests passed for the merged Phase 2
implementation; manual acceptance remains open.

The system is a Go modular monolith with `chi`, PostgreSQL, SQL-first queries
generated by `sqlc`, and an OpenAPI contract that generates TypeScript types.
The web app uses React, Vite, TanStack Router and Query, and Tailwind. Media
objects use an S3-compatible storage boundary. This architecture supports the
current marketplace without a separate service or internal chat system.

## Main Risks To Resolve

- The software flow has automated coverage, but Google sign-in and the full
  phone/browser journey have not completed manual acceptance.
- The repository has no evidence yet that real users find enough current offers
  in a chosen FUTA segment or that agents keep those offers accurate.
- Inquiry capture ends at a WhatsApp handoff. Agent follow-through and housing
  outcomes remain mostly outside Laivan, so trust claims must stay modest.
- Agents cannot apply, publish, correct, pause, or remove offer media in the web
  app. Operators cannot review applications or correct canonical facts there.
  There is no documented operational tool that closes these gaps for a pilot.
- Signed-in users have no visible account or logout control. Agents have no way
  to see or close recorded inquiries in Laivan. WhatsApp can carry the initial
  conversation, but it does not provide the platform with an outcome.

## Missing Product Journeys

The API foundation is further along than the usable product. A controlled pilot
can use a named operator and direct API tooling if that process is documented,
secured, and exercised. A self-service beta needs the following small journeys:

1. A person signs in, sees their account state, applies to become an agent, and
   can sign out. An operator reviews the application and activates or declines
   it for the correct campus.
2. An active agent contributes a property or accommodation type when needed,
   creates an offer, updates price and availability, manages its media, and
   archives a stale offer. An operator can correct shared facts without treating
   a contributing agent as the owner of the canonical record.
3. A student finds an eligible offer and records a question. The agent can see
   that inquiry with its offer context and close it. WhatsApp remains the
   conversation channel.

These are workflow gaps, not evidence that inspection, reservation, chat, or
payment features are required now. A lightweight way to report stale or
misleading offer information may become necessary as soon as real supply is
published; establish how the pilot handles such reports before adding public
trust claims.

## Priorities

### 1. Prove the integrated flow on real devices

Complete the manual acceptance matrix with a development Google client and a
phone browser. Check anonymous browsing, exact sign-in return paths, inquiry
persistence and retry, deliberate WhatsApp handoff, application activation,
ownership and stale-write denial, media removal, suspension, roles, logout,
CSRF, and audit evidence. Fix observed failures before adding another workflow.

### 2. Make onboarding and supply maintenance usable

Recruit and work with a small set of agents, curate a bounded set of properties
and accommodation types, and keep eligible offers and media current. First,
choose and document the pilot operating path: a secured, exercised operator
process using the existing API, or minimal web screens for application review
and supply changes. Build the missing agent and operator UI before describing
the product as self-service. Include account status and logout in that path.
Keep the scope to the existing APIs and the tasks needed to maintain current
offers. Check that real users find credible options and can ask useful questions.

### 3. Close the agent side of inquiries

The next bounded workflow feature is an agent queue for inquiries on that
agent's offers and a close action. It should preserve offer context and access
scope. It should not become chat, notifications, inspection scheduling, or a
dashboard expansion. Validate its shape with agents handling actual inquiries.

### 4. Learn from marketplace outcomes

Track a small set of operational measures: eligible offer depth by area and
accommodation type, searches that find a usable option, inquiry creation,
optional WhatsApp handoff, stale-offer reports, and agent follow-through.
Interpret these with direct conversations with students and agents. An inquiry
or a handoff is evidence of intent, not proof of a viewing or a successful
rental. Use observed failure points to improve inventory quality, discovery,
and trust signals.

### 5. Choose the next workflow from evidence

Inspection requests and reservation intent are distinct possible workflows.
Implement one only after the inquiry and supply pilot shows which coordination
problem recurs. Neither should imply guaranteed availability, acceptance, or
payment protection. Offline feedback and media delivery improvements may move
earlier if device testing shows they block the core flow.

## Deferred Decisions

Additional sign-in providers, account linking, and email/profile semantics are
tracked in GitHub issue #44. TanStack Start is conditional on a demonstrated
SEO or indexing need. Multi-campus expansion, automated duplicate detection,
ratings, payments, escrow, internal chat, and broad dashboards need their own
evidence and decisions. None is a prerequisite for the first useful FUTA
marketplace loop.

## How To Read The Documentation

- `docs/domain.md` describes the marketplace model, including future concepts.
  Its domain relationships are a design foundation, not a list of shipped
  features.
- This document records the current implementation boundary and priority order.
- OpenAPI, migrations, and tests record the shipped Phase 2 contract. Local
  planning and specification notes may be absent from a fresh checkout.
- `docs/vision.md` and `docs/context.md` explain the longer-term product intent;
  `docs/ui.md` and `docs/architecture.md` guide current design and engineering.
- Code, migrations, tests, and OpenAPI show what the application actually does.
  Historical implementation plans may contain superseded choices and do not
  override the current product decisions above.
